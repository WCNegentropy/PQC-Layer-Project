# Aegis OS / Browser / Runtime Expansion Plan
## Repo-Based Phased Implementation Plan for `WCNegentropy/PQC-Layer-Project`
**Based on current repository state as of 2026-04-21**

---

## 1. Executive Summary

The current repository is **not starting from zero**. It already contains a meaningful and usable foundation across the lower layers of the Aegis stack:

- **Layer 2 crypto is implemented**
- **Layer 3 transport is implemented**
- **Sanctuary server exists and is deployable**
- **Identity foundations are implemented**
- **Vault foundations are implemented**
- **CLI flows for identity/vault bootstrap exist**
- **Desktop app, web app, FUSE mount, full CRDT sync, and social runtime remain mostly planned or placeholder**

That means it should not be treated as a greenfield vision anymore. Instead, it should be expanded into **repo-grounded delivery** that turns the current Aegis codebase into:

1. a **private-node runtime**,
2. an **Aegis Browser** built from the Tauri desktop app,
3. a **vault-backed local application environment**,
4. a **shared-node and messaging system**,
5. and only later, a dedicated **immutable AegisOS distribution**.

The most important implementation reality visible in the current repo is this:

- `aegis-gateway` and `aegis-sanctuary` are the most mature parts of the platform.
- `aegis-identity` and `aegis-vault` provide real foundations, but are not yet production-complete.
- `aegis-social`, `aegis-desktop`, and `aegis-web` are still largely scaffolds/placeholders.
- Therefore, the correct path is **not** “build an OS now,” but:
  - finish the **private-node substrate**,
  - build the **browser/runtime shell**,
  - then harden into a dedicated appliance/immutable distro.

## 3. Strategic Reframing of the Attached Vision

The attached plan is directionally strong, but in repo terms it should be reframed as:

## 3.1 What “Aegis Browser” actually means in this codebase
In this repository, the “Aegis Browser” should become:

- the **primary UI/runtime shell** implemented in `apps/aegis-desktop`,
- backed by:
  - `aegis-vault` for local sovereign content,
  - `aegis-identity` for authentication and node identity,
  - `aegis-gateway` / adapted Sanctuary transport for private-node connections,
  - `aegis-social` for space serving, visits, messaging, and federation.

It should not initially try to replace a general-purpose browser. It should first become:

- a **vault-native browser/runtime**
- with controlled support for:
  - `vault://`
  - `node://`
  - `sanctuary://`
  - and optionally proxied `https://`

## 3.2 What “Aegis OS” should mean at this stage
Right now, “Aegis OS” should be treated as a **deployment target**, not a core code deliverable.

The core deliverable is:
- an **Aegis runtime stack** that can run on Linux/macOS/Windows.

Once that runtime is stable, an immutable distro can package:
- the runtime,
- the browser shell,
- the node services,
- the vault mount,
- the key management integration,
- and the update pipeline.

So the correct order is:

1. **Aegis runtime**
2. **Aegis Browser**
3. **Aegis private/shared node product**
4. **Aegis immutable appliance / distro**
5. **Later: AegisOS-branded hardware image**

## 3.3 What “Aegis Container” should mean in repo terms
The attached document recommends WASM, and that is still the right direction. But based on the repo’s current state, WASM should be deferred until after:

- private-node runtime exists,
- vault serving exists,
- browser sandbox exists,
- messaging and sync primitives exist.

WASM is best treated as:
- a **Phase 4/5 capability execution substrate**
- for user spaces, creator logic, automations, agent-like behaviors, and shared room logic.

It should not delay the core private-node/browser milestone.

---

## 4. Architectural North Star

The implementation goal should be:

> Every user runs a local Aegis private node that owns their identity, vault, profile, room, inventory, and messaging state. The Aegis Browser is the trusted UI/runtime shell for rendering local and remote spaces under strict sandboxing. Shared nodes are optional overlays, not mandatory dependencies. A dedicated immutable AegisOS image is a packaging and hardening layer on top of this runtime, not a separate architecture.

## 6. Recommended Delivery Philosophy

The biggest risk would be trying to build all of these simultaneously:
- OS image,
- browser,
- shared rooms,
- ActivityPub,
- WASM,
- full multi-device sync,
- platform integrations.

Instead, development should proceed in this strict order:

1. **Make the private node real**
2. **Make the browser shell real**
3. **Make direct visits real**
4. **Make sync and messaging real**
5. **Make shared rooms real**
6. **Make ecosystem packaging real**
7. **Only then freeze into immutable distro/hardware product**

# Phase 1 — Complete the Private Node Foundations
**Goal:** turn current identity + vault foundations into a true local private-node substrate.

This is the highest-priority implementation phase.

## Why this phase first
The Browser and OS concepts depend on:
- a real local identity anchor,
- a real local vault substrate,
- a real local node state model.

Without that, the desktop app is only a shell around placeholders.

## 1.1 Identity hardening (`aegis-identity`)

### Current repo basis
- `RootIdentity::generate()`
- `RootIdentity::issue_device()`
- DID document generation
- credential support
- auth challenge/response

### Required work

#### 1.1.1 Define persistent identity directory contract
Standardize on-disk layout for:
- root DID doc
- root signing material
- root exchange material
- device identity
- device attestation
- known peers / trust store
- discovery endpoint records
- rotation history
- backup metadata

#### 1.1.2 Formalize login identity lifecycle
Promote identity from “CLI-generated material” into:
- node owner identity
- device login identity
- session bootstrap authority

This should enable the desktop app to:
- load current identity,
- verify device attestation,
- unlock vault,
- initialize network runtime.

#### 1.1.3 Key rotation and recovery model
Implement design and scaffolding for:
- root key rotation
- device re-issuance
- lost-device revocation
- backup/export flow
- multi-device join flow

Even if some are MVP-limited, the storage and API shape should be designed now.

#### 1.1.4 Peer trust and trust store
Add structures for:
- known peer DIDs
- trust state
- blocklist / allowlist
- pinned discovery endpoints
- last-seen signed node records

#### 1.1.5 Signed node advertisement model
Use DID/service records as the basis for:
- current node endpoint
- protocol capabilities
- version compatibility
- room/public endpoint hints
- shared-node participation metadata

## 1.2 Vault hardening (`aegis-vault`)

### Current repo basis
- `VaultStore` with per-file AEAD
- manifest
- path-based key derivation
- social bootstrap
- minimal sync snapshot
- placeholder FUSE mount

### Required work

#### 1.2.1 Formalize logical vault schema
Expand the current social layout into a versioned schema covering:
- `social/space/`
- `social/character/`
- `social/inventory/`
- `social/profile/`
- `social/feed/`
- `social/messages/`
- `social/peers/`
- `social/shared_nodes/`
- `apps/`
- `runtime/`
- `cache/`

#### 1.2.2 Manifest evolution
Current manifest is enough for minimal storage, but future runtime needs:
- content hash
- media type
- schema classification
- created_at / updated_at
- tombstone flag
- sync generation
- author/device metadata
- optional capability labels

#### 1.2.3 Write/read API expansion
Add higher-level vault APIs for:
- JSON document read/write
- asset streaming
- directory listing
- metadata listing
- delete/tombstone semantics
- batched updates / transactions

#### 1.2.4 Integrity and repair tooling
Implement utilities for:
- manifest validation
- orphan blob cleanup
- missing blob detection
- nonce/key mismatch handling
- vault consistency repair

#### 1.2.5 Vault unlocking model
Define how vault master keys are handled:
- file-based MVP
- keyring-backed preferred path
- optional passphrase wrap
- future TPM/Secure Enclave wrapping

## 1.3 Real FUSE / virtual filesystem implementation

### Current repo basis
- `mount.rs` is placeholder only.

### Required work

#### 1.3.1 Implement read-only mount first
First production step should be **read-only** FUSE mount of logical vault paths.
This is safer and enough to:
- prove transparent decryption,
- support browser/editor access,
- validate path semantics,
- support diagnostics.

#### 1.3.2 Add write support second
Once read-path is stable:
- create/write/truncate/delete
- manifest update coordination
- atomic write staging
- crash safety

#### 1.3.3 Cross-platform strategy
- Linux: primary target first
- macOS: secondary
- Windows: likely separate abstraction later

Do not block Phase 1 on all platforms. Ship Linux first.

#### 1.3.4 Browser/runtime integration goal
The FUSE layer should make it possible for the browser/editor/runtime to treat selected vault content as normal files while preserving encrypted backing storage.

## 1.4 Local node state model

Introduce a new internal concept:
- **Private Node State**

This should represent:
- identity
- vault handle
- local discovery record
- current runtime config
- peer trust store
- active connections
- feature flags

This model can live initially in `aegis-social` or a new supporting crate/module, but it needs to exist before Browser logic is built.

## Deliverables
- production-ready identity/vault local substrate
- true vault storage contract
- read-only then read-write FUSE mount
- clear local private node state object

# Phase 2 — Turn `aegis-desktop` into the Aegis Browser
**Goal:** evolve the placeholder Tauri app into the primary Aegis user runtime.

This is the repo’s direct implementation of the attached Browser vision.

## 2.1 Desktop architecture target

`aegis-desktop` should become:
- local control plane,
- room renderer,
- vault browser,
- identity manager,
- peer visit client,
- node dashboard,
- eventually editor and app runtime.

## 2.2 Initial Tauri shell implementation

### Current repo basis
- `apps/aegis-desktop/src/main.rs` is a placeholder print-only app.

### Required work

#### 2.2.1 Build real Tauri bootstrap
Add:
- Tauri app setup
- command handlers
- state management
- platform init wiring
- structured error surfaces

#### 2.2.2 Core panels for MVP
Implement first UI panels:
- **Home / Node Status**
- **Identity**
- **Vault**
- **Spaces**
- **Visits**
- **Settings / Diagnostics**

#### 2.2.3 Backend service bridge
Tauri backend should expose commands for:
- load identity
- show DID and device info
- unlock/open vault
- read profile/space files
- list peers
- connect to peer
- inspect tunnel/session state

## 2.3 Aegis Browser protocol model

The attached plan proposes protocol handlers. That is correct and should be implemented in phases.

### 2.3.1 `vault://`
First and most important protocol.

Use it for:
- local room files
- profile data
- inventory assets
- character assets
- feed items
- editor previews

Requirements:
- path canonicalization
- access scoping
- content type detection
- read permission policy
- no arbitrary vault escape

### 2.3.2 `node://`
Second protocol.

Use it for:
- direct visits to another user’s private node
- direct asset/room retrieval over authenticated PQ transport

Requirements:
- DID-bound peer resolution
- transport session establishment
- remote content fetch API
- local sandbox rendering

### 2.3.3 `sanctuary://`
Third protocol.

Use it for:
- shared/community/creator spaces
- optional platform-hosted public rooms
- event spaces

### 2.3.4 Optional proxied `https://`
Do **not** make this a core dependency for the MVP.
Treat it as a later privacy utility:
- route standard web traffic through Aegis networking stack/proxy where appropriate.

## 2.4 Browser sandbox model

This is one of the most critical security tasks in the whole plan.

### Requirements
Remote space content must be treated like hostile web content.

The sandbox needs:
- strict CSP
- no ambient local FS access
- no access to arbitrary Tauri commands
- no unrestricted fetch
- no arbitrary shell execution
- controlled asset loading only from approved protocols
- per-space origin/capability model

### Recommended approach
Define a capability model by origin class:

- `vault://local-space/...`
  - local edit/render permissions
- `node://peer/...`
  - remote content render only
- `sanctuary://room/...`
  - remote content render only
- `app://ui/...`
  - trusted UI shell only

### Must-have MVP restrictions
- remote pages cannot call privileged backend commands directly
- remote JS cannot read arbitrary vault paths
- remote content cannot trigger system actions
- content must be loaded into isolated webviews or isolated contexts

## 2.5 Room renderer
Implement the first “space viewer” feature:
- load `social/space/index.html`
- resolve supporting assets
- render local personal space
- render remote fetched space in the same shell with a restricted execution model

## 2.6 Space editor
After viewer MVP:
- file tree for `social/space/`
- edit `index.html`, `style.css`, JSON metadata
- asset import
- preview mode
- validation/linting for unsafe capabilities

## Deliverables
- real desktop app
- real vault-native browser behavior
- protocol handling
- sandboxed room rendering
- local space editor/viewer

Implement first end-to-end visit flow:

Add policies for:
- public room access

The first complete Layer 7 proof should be:
- two local Aegis instances on one machine,
- each with its own identity and vault,
- direct visit from A to B,
- remote room rendered,
- basic peer presence shown.

This milestone should be considered the most important target after desktop bootstrap.

# Phase 4 — Complete CRDT Sync and Multi-Device State
**Goal:** evolve the current sync placeholder into a real multi-device and multi-node state engine.

## 4.1 Current repo basis
`aegis-vault/src/sync.rs` currently contains:
- `SyncEntry`
- `SyncSnapshot`
- last-writer-wins merge logic
- validation

This is a good seed, but still only a data model helper.

## 4.2 Required sync architecture

### 4.2.1 Move from snapshot merge to operation-based sync
Implement:
- operation log
- per-device actor IDs
- monotonic sequence numbers / vector clocks where needed
- tombstones
- replay and compaction rules

### 4.2.2 Data classes
Different vault data types should not all share identical semantics.

Recommended categories:
- structured profile docs
- room metadata
- inventory ownership records
- feed items
- message logs
- room presence state
- binary asset blobs

### 4.2.3 Conflict strategy by data type
Use different semantics where appropriate:
- profile/settings: LWW or field-level merge
- directory membership: OR-Set
- feed/messages: append-only/event log
- room state: CRDT state doc
- binary assets: content-addressed dedupe with manifest refs

### 4.2.4 Network sync transport
Sync should operate over existing authenticated encrypted channels where possible:
- direct device-to-device
- private node to owned secondary device
- optional relay/shared infra later

### 4.2.5 Offline-first model
The system should tolerate:
- edits while disconnected
- delayed merge
- deterministic conflict handling
- resumable blob transfer

## 4.3 Sync MVP scope
The first sync milestone should cover:
- profile
- room metadata and room files
- character state
- inventory documents
- feed posts

Do not block on full message sync or group state sync for the first deliverable.

## 4.4 Test plan
Add integration tests for:
- concurrent edits on two devices
- delete/update conflict
- blob present on one side only
- interrupted sync recovery
- deterministic merge replay

## Deliverables
- real sync engine
- multi-device private node continuity
- basis for shared nodes and offline use

# Phase 6 — Browser-to-Runtime Expansion and WASM Containers
**Goal:** introduce programmable, sandboxed execution within the Aegis environment.

## 6.1 Why this phase comes later
WASM is strategically correct, but not first. A container runtime only becomes valuable once:
- spaces exist,
- peer visits exist,
- shared nodes exist,
- creators need programmable logic.

## 6.2 WASM execution model
Embed a WASM runtime in Rust, likely in a dedicated crate or within `aegis-social`/runtime layer.

Potential uses:
- room scripts with bounded capabilities
- creator plugins
- automation tasks
- content transforms
- item logic
- local assistant-like workflows
- sandboxed compute exchanges

## 6.3 Capability system
WASM modules must use explicit capabilities:
- read scoped vault paths
- write scoped vault paths
- network to approved peer/session scope only
- limited storage quota
- CPU/runtime budget
- no unrestricted host access

## 6.4 Distribution model
WASM packages should be:
- signed
- versioned
- capability-declared
- optionally DID/creator-attested

## 6.5 Relation to Browser
The Browser should be able to:
- install a package
- inspect requested capabilities
- enable/disable it
- execute it within a room or local runtime context

## Deliverables
- embedded sandboxed execution
- creator/plugin substrate
- future foundation for “Aegis app ecosystem”

# Phase 9 — Immutable Linux Distribution / AegisOS
**Goal:** package the now-mature Aegis runtime as a dedicated appliance-like environment.

This is where the attached OS vision should land.

## 9.1 Correct interpretation
AegisOS should be:
- a hardened packaging/deployment profile for the runtime,
- not a separately engineered kernel/platform.

## 9.2 Recommended distro strategy
The attached note suggests Alpine or NixOS / Fedora CoreOS-like direction.

Repo-grounded recommendation:
- prototype with a **minimal immutable Linux base**
- prioritize:
  - secure boot compatibility
  - read-only root
  - signed updates
  - easy system service management
  - strong reproducibility

NixOS or Fedora CoreOS/Silverblue-style thinking is architecturally more aligned with long-term immutable operations than an ad hoc custom distro.

## 9.3 AegisOS package contents
The image should ultimately include:
- Aegis runtime services
- Aegis Browser
- vault mount service
- node discovery/update agent
- key storage integration
- update service
- diagnostics and recovery tooling

## 9.4 System behavior target
Boot flow should become:
1. verified boot
2. unlock identity/device context
3. unlock vault
4. start local node services
5. launch Aegis Browser as primary shell
6. optionally expose shared-node or admin services

## 9.5 Hardware integration later
Only after distro maturity:
- TPM sealing
- Secure Enclave / hardware-backed keys where relevant
- dedicated appliance/hardware SKU
- kiosk-like/browser-shell mode

## Deliverables
- immutable Aegis appliance image
- dedicated private-node device experience
- bridge from app platform to sovereign endpoint product

## 10. Key Design Rules to Preserve During Implementation

## 10.1 Do not let shared infrastructure become mandatory
Everything should keep reinforcing:
- private node first,
- shared nodes optional,
- bootstrap infra off data path.

## 10.2 Do not let the browser become a privilege escalation surface
Remote user HTML/JS must be treated as hostile by default.

## 10.3 Do not couple the vault API too tightly to one UI
The CLI, desktop app, future mobile app, and shared node runtime should all be able to use the same vault substrate.

## 10.4 Do not overbuild the OS before the runtime exists
The runtime is the product; the OS is a packaging/hardening strategy.

## 10.5 Keep cryptographic boundaries explicit
Transport, identity, storage, messaging, and federation should remain separable layers.

## 11. Risks and Mitigations

## 11.1 Risk: building too many surfaces at once
**Mitigation:** enforce milestone gating around private node → browser → visits.

## 11.2 Risk: insecure browser integration
**Mitigation:** capability-based protocol model, isolated contexts, strict CSP, no raw backend exposure.

## 11.3 Risk: sync complexity explosion
**Mitigation:** phase sync by data class; start with snapshots evolving to op logs.

## 11.4 Risk: identity model drift
**Mitigation:** define stable on-disk identity contract before desktop and federation work.

## 11.5 Risk: Sanctuary role confusion
**Mitigation:** consistently present Sanctuary as:
- reusable server primitive,
- shared-node substrate,
- optional infra,
- not central architecture.

- **Do use the existing transport/identity/vault foundations as the launchpad**

This matches both:
- the attached strategic vision,
- and the actual current state of the repository.
